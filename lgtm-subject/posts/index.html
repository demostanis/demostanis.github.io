Chapter II
#

Introduction
#

An observability stack is a set of tools and technologies designed to provide comprehensive visibility and insight into the performance, health, and behavior of applications and their underlying infrastructure. Technologies comprising an observability stack include logs, metrics, tracing, profiling, etc.

There exist many different observability solutions like DataDog, ELK stack, CloudWatch… For this subject, a LGTM (Loki, Grafana, Tempo, Mimir) stack will be used.

In the middle of this stack lives the OTel Collector, whose job is to unify telemetry sources and receivers.

Chapter III
#

Goals
#

In this subject, you will implement a basic website communicating with your backend, which will implement observability.

This website will have to let the user run untrusted code on your server using WASM/WASI, and upload that code and its output on IPFS.

Everything will be running in Kubernetes.

Chapter IV
#

General instructions
#

IV.1 Restrictions
#

You may use any language and tool of your choice for this project. You should however take into account before choosing a programming language that it has support for OpenTelemetry and IPFS (unless you want to call its HTTP API directly) (Go is a good candidate).

You may not use a cloud service such as Grafana Cloud. Everything should run in a local Kubernetes cluster (such as minikube, kind, k3d…).

IV.2 Observability stack
#

A LGTM stack may not always composed of Loki, Grafana, Tempo and Mimir. For example:

  • Jaeger is often used instead of Tempo.
  • Alloy instead of OTel Collector.
  • Prometheus instead of Mimir.

You may switch those tools, as long as Grafana stays the visualization tool.

IV.3 Security considerations
#

Since the code your web app will allow to run will be untrusted, it is vital to restrict its power.

  • It must not have network access (or with a domain whitelist).
  • It must not have filesystem access (or with a path whitelist).
  • It must not use more memory than a pre-defined size (e.g. 10MB).
  • It must not run more than a pre-defined time limit (e.g. 5 seconds).
  • Its output must be truncated if it’s bigger than a pre-defined limit (e.g. 10kB).

Since it is easier to do this with a WASI runtime, it is advised to choose a language that can output to WASM. You can use a language that does not support WASM, as long as it still runs sandboxed (with seccomp? Landlock? Cosmopolitan pledge/unveil? bubblewrap? SELinux? Capsicum? Custom LSM??).

Chapter V
#

Mandatory part
#

Your web app should be accessible at lgtm.local (you might need to modify /etc/hosts in your VM or run a local DNS resolver), through an ingress/gateway.

You need to choose a programming language that your backend will compile to WASM. It can be the same language as the one the backend is written in. You can use any library to compile code, or even write your own compiler, such as cc1.

The frontend should follow these rules:

  • There should be a small code editor, with a code example of the language you’ve chosen.
  • There should be a Run button to compile and run the user code.
  • When the user clicks on that button, the user should get a visual feedback that their code is compiling.
  • When the code fails to compile or run, the user should see the compiler/runtime errors.
  • When the code compiles and runs successfully, the user should see its output, along with an IPFS link.

This IPFS link must look like ipfs.lgtm.local/ipfs/<cid>, pointing to a directory containing the user code and its output, in your local IPFS gateway. This directory should be accessible from the outside through a public gateway such as ipfs.io using the same CID (https://ipfs.io/ipfs/cid).

Since IPFS is a peer-to-peer network, your computer needs to be accessible from the outside world. If using NAT, this might not be feasible without changing the router’s configuration. If IPv6 and UPnP are not available, IPFS will try to fallback to DCUtR hole punching, but it might still fail on some networks.

You can try to use a mobile network during the defense, or host your cluster on a remote server. If this is still not feasible, it will have to be correctly explained to your evaluators.

More information at https://docs.ipfs.tech/how-to/nat-configuration/.
